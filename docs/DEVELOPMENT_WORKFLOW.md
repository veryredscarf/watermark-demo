# 开发、实验与修复流程

版本：0.2；适用于 Agent 和人工开发者。此流程用于保持结论可复现，不能代替代码审查与安全审查。

## 1. 任务入口

1. 读取 `AGENTS.md` 指定文件，检查当前目录和版本状态。
2. 选定一个需求编号（见 `REQUIREMENTS.md`），写清本轮要改变的用户可见行为和不变的安全约束。
3. 若需求无验收标准，先补充标准；若改变信任边界、标识生成、日志策略或失败策略，先更新架构和决策记录。
4. 暗水印改动先确认 BENCHMARK_PROTOCOL.md 的数据分组、基线版本、冻结阈值和 T0/T1 状态；T1 不通过时不得跳到平台转发优化。
5. 拆成可独立验证的小改动。实现前列出最短的验证方法。

## 2. 实施与验证

1. 先实现最小闭环，再扩展兼容性；每个改动保持单一责任。
2. 运行必要的静态检查、单元/接口/浏览器实验。测试必须对应真实风险或验收项。
3. 对水印功能至少覆盖：正常渲染、身份切换、过期标识、网络失败、缩放/滚动/弹窗、打印、清理卸载、恶意 DOM 修改、核验错误码。
4. 保存代码提交、参数、样本清单 SHA-256、精确命令、退出码、环境、逐图结果和测量口径。结果分为“通过 / 失败 / 未运行”，禁止只写“测试正常”。
5. 对性能和视觉指标记录基线与水印启用后的相同场景对照；不能凭主观感觉宣称达标。

## 3. 缺陷修复闭环

1. 在 `EXPERIMENT_LOG.md` 建立实验条目：复现步骤、输入、环境、预期、实际、证据。
2. 写出可证伪的原因假设，并指出验证手段。
3. 一次只更改一个主要变量；若必须合并修改，说明原因。
4. 用原始失败条件复验，再跑相关回归；记录修复前后结果和仍未覆盖的边界。
5. 结果成立才更新需求状态、架构和 `PROJECT_STATE.md`；不成立则保留失败证据继续实验。修复样本进入固定回归集，封存验收集不得用于调参。

## 4. 决策与记忆

- `PROJECT_STATE.md` 是唯一“现在做到哪一步”的快照；不得从聊天记忆推断进度。
- `DECISIONS.md` 记录稳定选择和理由；新决定不抹去旧决定，标记被取代关系。
- `EXPERIMENT_LOG.md` 记录原始观察；判断必须能追溯到具体实验编号。
- “事实”“推测”“待确认”分别标记。没有验证数据时，不写“解决”“安全”“兼容”之类结论。
- 每轮结束时更新状态，写明下一步最小动作和阻塞条件；中断后按状态文件恢复。

## 5. 合并与发布门槛

- 需求编号与验收证据一一对应；未通过的项明确列出，不隐含放行。
- 高敏感数据路径完成身份与权限校验、标识签发、核验和失败策略验证。
- 完成所声明浏览器及真实业务页面的回归；打印与下载链路分别验证。
- 安全负责人审查密钥、个人信息、审计权限与日志留存；代码评审检查可维护性和回滚方式。
- 灰度发布应有监控、告警阈值、回滚开关和回滚演练。发布后记录实际结果。
