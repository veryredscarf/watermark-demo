# 本地持久化方案（待整体方案审阅）

版本：0.1；2026-11-04。适用于首个需要签发并在服务重启后核验水印的 Node.js 功能版本。当前仓库 S1 仍是内存演示，本文件尚未实现。

## 1. 选择与边界

选用本机 SQLite 数据库文件，不部署单独数据库服务。T0 纯编解码固定向量可以只用内存；从首次服务端签发实际水印租约、准备 T1 原图闭环开始，租约映射与审计必须先写入本地文件并完成提交，才能返回受保护内容。实验使用虚构身份和数据；未获批准前不接入真实业务身份。

开发环境默认将数据库放在仓库已忽略的 `artifacts/runtime/watermark.sqlite`。部署时通过 `WATERMARK_DB_PATH` 指向仓库外的本机数据目录，由服务账号独占访问。该路径不是浏览器可访问的静态资源目录；数据库、日志、备份、密钥和真实截图均不得提交 Git。服务端生成图块的密钥另由受控配置提供，不写入数据库文件。

## 2. 最小数据模型

| 表 | 最小字段与约束 | 用途 |
| --- | --- | --- |
| `schema_migrations` | 版本、应用时间 | 升级与回滚核对 |
| `leases` | `lease_id` 主键；可见码、暗码各唯一；租户、主体引用、资源引用、签发/过期时间、状态、算法与策略版本 | 明暗码映射及历史核验 |
| `access_events` | 访问事件 ID、租约 ID、时间、资源引用 | 核对访问事实 |
| `audit_events` | 事件 ID、类型、操作者引用、案件号、请求 ID、目标租约、时间、结果 | 签发、核验和调查留痕 |

调查图片本体不存入这些表；仅存 SHA-256、受控存储引用和保留期元数据。真实样本保管方式待业务与安全负责人确认。

## 3. 写入与故障语义

签发时在同一事务里写入租约、访问事件和签发审计，确认提交成功后再返回水印及受保护内容。可见码和暗码冲突时重新生成并重试；唯一约束是最终保护。磁盘不可写、数据库打不开、迁移失败或提交失败时，高敏感内容不返回，接口给出稳定错误码并记录不含敏感正文的故障信号。

服务启动时检查数据库路径、模式版本、所需表和权限；禁止因文件缺失自动切换回内存审计。服务重启后可按同一可见码或暗码查回原租约与审计。会话认证仍由业务身份系统负责，演示会话 `Map` 不作为生产会话方案。

## 4. 备份、恢复与部署限制

开发实验可定期生成一致性备份；真实数据进入前须确定备份频率、加密/磁盘保护、权限、保留期与恢复演练。运行中备份使用 SQLite 支持的一致性备份方式，不能只随意复制正在写入的主文件。备份文件放仓库外受控目录。

此方案面向单机、单服务实例。若未来多个服务节点同时签发或需要跨机器共享数据，应改用集中式事务型存储；不把 SQLite 数据库文件放在网络共享盘供多机同时写入。HTTP 接口与数据访问层保持独立，迁移时用同一契约测试复核。

## 5. 首个版本的验收

1. 签发一条虚构租约，记录明暗码及审计；强制终止并重新启动 Node.js 服务，核验仍返回同一租约。
2. 模拟并发或重复码，确认唯一约束与事务回滚生效，不产生半条租约或孤立访问事件。
3. 模拟数据库只读、磁盘写入失败和损坏文件；高敏感内容不返回，且不会静默降级到内存。
4. 制作一致性备份，在新目录恢复并核对记录数、唯一映射、算法版本及审计；记录命令与结果。
5. 运行 T1 原图实验前完成以上检查；实际业务上线前另做权限、保留期和真实系统验收。
