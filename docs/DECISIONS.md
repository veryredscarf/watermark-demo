本文件保留已经接受、提议和被取代的设计决定。变更时新增条目并注明取代关系，不直接改写历史理由。

## ADR-001：先建立规范与证据流程

- 日期：2026-11-02
- 状态：已接受
- 背景：项目预计多次实验与修复，工作区初始为空；用户要求避免跨轮次记忆混乱。
- 决定：用 `AGENTS.md` 作为入口，`PROJECT_STATE.md` 作为唯一进度快照，以需求编号、决策编号和实验编号连接代码改动与证据。
- 影响：功能开发必须先有需求、设计和验收；每轮收尾更新状态。

## ADR-002：服务端签发可见追溯码

- 日期：2026-11-02
- 状态：首版设计基线
- 背景：客户端可被访问者修改，不适合作为身份和签发权威。
- 决定：服务端在认证和资源授权后生成高熵随机码，保存身份/资源/访问记录映射；前端只显示。调查通过受权服务端核验。
- 影响：需要业务 API 集成和审计存储；单独引入水印 SDK 不能完成可信溯源。

## ADR-003：首版工程技术方向

- 日期：2026-11-02
- 状态：已被 ADR-005 取代
- 原方案：TypeScript 的框架无关 SDK；Vite 演示页；独立服务端演示接口；真实业务后端沿用企业现有技术栈。
- 取代原因：用户明确指定 Vue 3 前端与 Node.js 首版后端，并要求达到上线标准后才考虑 Java 或其他服务端语言。

## ADR-004：客户端水印的证据地位

## ADR-005：Vue 3 前端与 Node.js 首版后端

- 日期：2026-11-02
- 状态：已接受；取代 ADR-003
- 决定：首版业务前端使用 Vue 3 + TypeScript + Vite；水印核心逻辑独立于 Vue，Vue 3 提供组合式函数/组件适配。首版服务端使用 Node.js + TypeScript，开发与上线以受支持的 Node 24 LTS 为基线。实验与修复期间保持 Node.js 实现；达到上线标准后才评估 Java 或其他语言。
- 理由：遵循用户明确技术选择。Vue 官方脚手架采用 Vite 并支持 TypeScript（[Vue 官方说明](https://vuejs.org/guide/quick-start.html)）。Vite 只转译 TypeScript，因此独立类型检查是构建门槛（[Vite 官方说明](https://vite.dev/guide/features)）。本机默认 Node 20 已停止维护，工作区提供 Node 24；生产不能以 Node 20 作为基线（[Node.js 发布状态](https://nodejs.org/en/about/previous-releases)）。
- 影响：项目结构按 `apps/web`、`apps/api`、`packages/watermark-core`、`packages/watermark-vue` 和共享契约组织；具体包管理器与依赖版本在首次工程初始化时锁定。

## ADR-006：服务端语言迁移门槛

- 日期：2026-11-02
- 状态：已接受
- 决定：先完成 Node.js 版本的需求、验收、压测、安全审查和灰度；之后才单独评估 Java/其他语言。前后端通过版本化 HTTP/JSON 契约、统一错误码、UTC 时间和契约测试隔离实现；Vue 代码不得依赖 Node.js 私有数据结构或数据库表。
- 迁移准入：生产指标、故障恢复、调查流程和真实业务验收达标；有明确迁移动机、成本收益与回滚方案。
- 迁移完成：候选服务实现通过同一套契约、授权、租户隔离、签发唯一性和历史核验测试；灰度对照无语义差异后再切换。

## ADR-007：S1 工程与演示接口

- 日期：2026-11-02
- 状态：已接受
- 决定：使用 pnpm 工作区，Vue 3 + TypeScript + Vite 作为演示前端，Node.js 24 标准库 HTTP 服务作为演示后端。Node.js 端先使用 JavaScript ESM，避免为了实验接口增加服务端编译层；生产重构时保持 `API_CONTRACT.md` 不变。依赖具体版本由锁文件固定。
- 约束：演示登录仅用于虚构身份测试；内存会话和签发记录不能用于生产。达到上线标准前必须接入企业身份系统、持久化审计、限流与密钥/权限审查。
- 验收：R-01、R-02、R-05、R-06 的最短闭环，加上 R-03、R-04、R-09 的基础生命周期行为；运行接口和浏览器实验并记录。

## ADR-010：原图优先与 A→B→C 硬门槛

- 日期：2026-11-03
- 状态：已接受，指标为待验证目标
- 决定：先证明 A 本地原始截图可稳定识别；T1 失败时阻断更高层级验收。A 电脑非原图发送、B 手机普通保存并再次非原图发送、C 保存最终图片是暗水印发布硬门槛；结果必须逐平台、逐设备矩阵统计，不能用可见码成功率替代。

- 说明：指标尚未实测；未达标时不发布对应暗水印能力。

## ADR-012：实验阶段与正式调查的存储分界

- 日期：2026-11-04
- 状态：已被 ADR-013 的新提案取代；保留原始建议和理由
- 背景：当前 S1 在 `apps/api/server.mjs` 用内存 `Map` 保存会话和租约，数组保存审计；用户询问项目初期是否必须部署数据库。
- 建议：T0/T1 虚构数据的单次实验无需数据库服务，可使用内存映射与固定真值清单。需要跨进程重启、跨天或真实 A→B→C 样本复查时，先加入持久化；单机研究环境建议 SQLite 文件。正式系统上线必须有可靠的事务、唯一约束、备份恢复、租户隔离和审计留存，多实例部署再选集中式存储。
- 边界：内存数据丢失不可恢复，不能作为生产审计。数据库文件、真实样本和原始调查数据不提交 Git；只提交模式定义、迁移脚本、虚构测试数据和脱敏结果。具体生产引擎仍由部署与安全要求决定。
- 依据：SQLite 官方说明其为嵌入式、无独立服务进程的事务型数据库（https://www.sqlite.org/serverless.html）；多主机共享数据库文件或网络文件系统不适合直接沿用单机 SQLite WAL 方案（https://www.sqlite.org/wal.html）。

## ADR-013：首个签发版本使用本机 SQLite

- 日期：2026-11-04
- 状态：提案，响应用户提出的服务自行重启约束；待整体方案审阅
- 背景：ADR-012 原建议 T0/T1 可用内存映射，但服务可能在截图调查前自行重启，导致签发记录丢失。
- 建议：仅 T0 纯编码向量使用内存。首个服务端签发/核验功能版本即使用本机 SQLite 文件；事务写入租约、明暗码映射、访问事件和审计，提交成功后才返回受保护内容。部署文件路径通过配置放在仓库外；开发文件位于已忽略的 `artifacts/`。重启、写入失败、唯一约束和备份恢复测试在 T1 前完成。
- 边界：当前内存 S1 原型保持未验收基线，尚未实施数据库。真实身份、密钥、截图本体不随意写入本地文件；真实数据进入前要确定文件访问权限、磁盘保护、保留期和备份策略。多实例或跨主机部署另选集中式存储。
- 协作：运行时数据库文件及侧文件不入 Git；共享版本化迁移、纯虚构种子数据和预期结果，各开发者在本机生成数据库。初始化命令与文件路径待功能分支实施时固定。
- 依据：SQLite 官方说明其无需独立服务进程（https://www.sqlite.org/serverless.html），事务可保证单次提交的原子性（https://www.sqlite.org/transactional.html），运行中备份应使用一致性备份方式（https://www.sqlite.org/backup.html）。具体模型和验收见 LOCAL_STORAGE_PLAN.md。

## ADR-014：首版覆盖全部列表页，裁剪恢复按尺寸档声明

- 日期：2026-11-05
- 状态：用户已明确首版范围与截图保存授权；裁剪档阈值仍待实验验证
- 背景：用户明确首版应保护目标系统的所有列表页面，并提供四张不同列表结构截图；实际截图可能是系统工具截取的任意大小区域，而非完整浏览器画面。此前 ADR-011 的“不入 Git”截图处理规则被最新明确授权局部取代。
- 决定：四张指定截图原样纳入 `docs/assets/reference-list-pages/`，只用于界面参考并记录散列，不作为暗水印实验样本。首版实际接入范围按未来正式路由清单盘点全部列表页；SDK 验证页仅覆盖四类参考形态。T1 完整图硬门槛保留，另以 T1-C/T4 对原生区域截图和事后裁剪分档测试；只有通过的尺寸档可声明恢复能力，任意小图不预先保证。
- 影响：R-16 范围扩大，新增 R-17；BENCHMARK_PROTOCOL.md 的 T4 从单一约 50% 裁剪改为变尺寸分档。真实系统没有源码/正式接入点和路由清单，R-16 继续未完成；原始社交平台样本仍不入 Git。
