# 网页水印与泄露溯源项目开发方案

版本：0.2（暗水印技术方案待审阅）
日期：2026-11-02
状态：实施基线草案；生产接入条件见 `PROJECT_STATE.md`。

## 一、目标与成功标准

面向企业受保护网页，在展示敏感内容时叠加可辨认且可追溯的水印。水印标识由服务端根据已经认证和授权的访问签发；发现泄露截图后，可通过标识查询访问记录，输出带有证据来源和置信度的调查报告。

首版成功标准：

1. 指定页面能稳定展示当前访问的水印，并在用户切换、资源切换、会话到期时正确更新或关闭。
2. 从真实页面截图中读取的标识能被服务端核验并关联至唯一签发记录；无效、过期、跨租户标识不能被误判为有效访问。
3. 水印不阻断鼠标、键盘、屏幕阅读器和主要业务操作；在约定浏览器与分辨率下通过视觉、性能和打印测试。
4. 核验流程保留原始样本、查询日志、证据链与调查人操作记录；报告明确说明水印只是线索。
5. 关键失败场景可监控、可回滚；敏感数据在没有有效签发时仍由服务端访问控制保护。

## 二、范围与边界

### 首版范围（P0）

- 企业内部网页及其首批指定业务页面；桌面浏览器优先。
- 受保护业务区域平铺可见水印和低可见度 Canvas 暗水印；两条通道映射同一次服务端授权访问。顶栏、侧栏、弹窗及全屏的实际覆盖策略按接入页验证。
- 服务端签发、查询、核验、审计；前端 SDK 初始化、更新、卸载及异常状态回报。
- 基本打印样式与业务页接入示例；受权调查员可进行可见码核验和图片暗码提取。
- 匿名演示用户和样例敏感页，供端到端验证。

### 后续阶段（P1/P2）

- 真实系统的下载文件、PDF、图片、报表由各自的生成链路添加水印；不能假定屏幕叠层会进入导出物。
- 多业务线与多租户策略管理、灰度开关、报表、告警联动、识别辅助工具。
- 任何新增社交平台、拍屏或更强图像加工链路，仅在真实样本集上实测通过后列为支持；不能预先宣称“隐形水印可靠”。

### 明确限制

- 具备浏览器控制权的用户可通过开发者工具、脚本、扩展或改图移除/伪造客户端水印；前端无法阻止摄像头拍屏或通过其他 API 获取原始内容。
- 截图上的可见身份或追溯码均不足以单独定责。调查须交叉核对签发记录、资源访问、时间和原始样本保全情况。
- 跨源 iframe、浏览器原生 PDF 查看器、操作系统截图、第三方原生客户端不在单个网页 SDK 的控制范围。

## 三、交付架构

1. `packages/watermark-core`：与框架无关的 TypeScript 水印核心逻辑。
2. `packages/watermark-vue`：Vue 3 组件/组合式函数与生命周期适配。
3. `apps/web`：Vue 3 + TypeScript + Vite 业务演示和受权核验界面。
4. `apps/api`：Node.js + TypeScript 签发、续期、核验、策略和审计 API。
5. 规范、威胁模型、接口契约、测试数据、实验记录、运维和接入手册。

首版后端维持 Node.js 直至上线标准达成；Java 或其他语言仅作为后续可选迁移，按 `DECISIONS.md` 的 ADR-006 验证。

详细数据流见 `ARCHITECTURE.md`，验收编号见 `REQUIREMENTS.md`。

## 四、实施阶段与里程碑

原先约 4–6 周的估算只覆盖可见水印演示与初步接入，不适用于新增暗水印及真实双次转发实验，现撤销该总工期承诺。完成样本采集可行性调查后再估算。

| 阶段 | 核心工作 | 出口条件 |
| --- | --- | --- |
| S0 Git 与方案 | 独立分支保存现有未验收原型；审阅需求、威胁模型、技术候选和基准协议 | 用户确认技术方案与门槛；无新功能代码 |
| S1 现有演示基线 | 核对已有 Vue 3 + Node.js 可见水印原型 | 明确现有通过/未运行项，不把演示当生产验收 |
| S2 原图暗水印闭环 | 编码、绘制、截图、提取、负样本与视觉检查 | T0/T1 和负样本硬门槛通过，失败样本进入回归 |
| S3 真实转发研究 | 微信和企业微信 T2/T3/T4 样本采集，按单变量实验改进 | 各格子达到 BENCHMARK_PROTOCOL.md 的门槛；未达则不得宣称支持 |
| S4 生产接入 | 拿到实际系统源码或正式接入点后，完成身份、持久化审计、权限、业务页面、监控、灰度和回滚 | R-16 真实系统及安全、业务验收通过；支持范围按真实证据发布 |

算法路线、数据流和接口草案见 WATERMARK_RESEARCH_PLAN.md；样本、指标和失败处理见 BENCHMARK_PROTOCOL.md。
用户提供的业务系统截图只作界面结构参考。当前无源码，先交付可接入 SDK 和虚构数据验证页；真实系统接入设计与未决项见 TARGET_SYSTEM_INTEGRATION.md。
## 五、职责分工

| 角色 | 主要责任 |
| --- | --- |
| 产品/数据负责人 | 指定水印页面、数据分级、展示文案和验收场景 |
| 前端负责人 | SDK、适配器、可访问性、浏览器与页面集成 |
| 后端负责人 | 服务端授权、签发/核验、存储、审计和故障策略 |
| 安全负责人 | 威胁模型、密钥、隐私、调查权限、对抗评估 |
| 测试负责人 | 场景矩阵、回归、性能与实验记录 |
| 运维负责人 | 部署、指标、告警、备份、回滚和留存策略 |

小团队可一人兼多职，但安全和生产验收需要独立复核。

## 六、质量与发布策略

- 每个需求编号对应可执行或可观察的验收证据；安全相关缺陷优先修复。
- 先在演示页形成端到端闭环，再用一套真实业务页检验兼容性。
- 先白名单用户/页面灰度，观测签发失败率、渲染异常率、页面性能、支持工单与核验准确性，再逐步扩大。
- 高敏感页的水印签发失败采取服务端拒绝返回敏感数据的策略；具体降级规则需由业务和安全负责人确认。
- 回滚应能独立关闭 SDK 渲染、撤回页面接入或切换服务端策略；不能因关闭视觉水印而放开服务端权限检查。

## 七、主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 用户自行移除或伪造水印 | 明确证据等级；服务端记录与样本交叉核对；下载/导出独立处理 |
| 误认责任人 | 追溯码唯一签发；调查报告展示上下文和局限；双人复核重大结论 |
| 水印遮挡或性能下降 | 密度/透明度配置、复杂 UI 场景回归、对照测量 |
| 隐私或审计数据过量 | 最小化字段、受权访问、有限保留期、调查访问也留痕 |
| 服务不可用 | 高敏感页服务端保护；灰度、告警、回滚与恢复演练 |
| 业务内容经其他通道泄露 | 将 API、打印和导出分别纳入保护与审计范围 |

- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)：页面可访问性验收参考。
- [MDN 打印样式说明](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Media_queries/Printing)：屏幕与打印是不同媒介，需分别验证。
